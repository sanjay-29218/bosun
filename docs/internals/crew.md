# Crew in T3 Code

T3 Code already gives a person durable threads and a provider runtime. Crew mode adds stable identities and durable coordination between those threads. A top-level bot (Captain, or one a person adds) owns each project. It receives a person's request for that project, delegates the work to the project's manager, and reports the linked result. The owning environment keeps the crew state and runs its providers; web, desktop, and mobile are clients of that environment. "Bot" is reserved for the top-level bots that own projects; everything here is crew.

## The boundaries that matter

- A **role** is reusable, environment-wide configuration: name, instructions, provider instance and model, T3 runtime mode, and allowed crew tools. Project manager, Planner, Designer, Builder, QA Tester, and Reviewer are starting roles, not an exhaustive enum. Users can add any role. Roles marked `autoCreateForFeature` join every new feature's crew.
- A **crew member** is an independently addressable instance of a role. It snapshots the role's revision, then has its own configuration and scope. A project's manager belongs to the project and is created the first time a request or feature needs it; a feature's crew members belong to the feature. Editing a role must not silently rewrite existing members or runs.
- A **run** starts one T3 thread for one task. The run snapshots its member's instructions and tool grants. A continuation uses that thread; a later task gets another run. The thread remains the source for provider activity, approvals, checkpoints, and diffs. A started turn is not a completed task.
  Roles, members, and runs have separate storage in [the migrations](../../apps/server/src/persistence/Migrations.ts). Earlier migration files retain older storage shapes so existing databases can upgrade; later migrations rename and transform them. Member IDs such as `bot-captain` and `bot-manager:<project>` and the `bot-run:` thread prefix predate the Roles rename and stay, because stored runs and grants reference them. The `crew_handoffs` tables from the retired handoff path stay for older databases; nothing reads them. The current store and validation live in [CrewStore](../../apps/server/src/crew/CrewStore.ts) and [CrewService](../../apps/server/src/crew/CrewService.ts).

## Bots as actors

A bot is not a crew member, but it acts in crew runs: a request to a project runs as the project's bot. Its authority comes from ownership, not grant rows. A bot only gets new runs on projects it owns, and a bot's run may delegate to members of that run's project ([CrewStore.canDelegate](../../apps/server/src/crew/CrewStore.ts)). Checking the run's project instead of current ownership means moving a project to another bot never strands a request or feature that is already running; only new work goes to the new owner. Ownership is `project.botId`, recorded by project events, so it replays like the rest of the project.

A headquarters lives as long as its bot, so its provider conversation keeps growing. By default the provider compacts it. A person can instead start it over (`bots.startNewSession`), or set the bot's `longConversation` to `new-session` so the crew does it past [`FRESH_START_TOKENS`](../../apps/server/src/crew/headquartersFreshStart.ts) after a quiet spell. Either way `thread.conversation.restart` retires the provider conversation and a briefing with the bot's current instructions and last few messages opens the next one. The thread keeps its messages for the person, but the model loses them, so anything a bot must still know later belongs in records it reads through tools (projects, features), not only in its chat.

## Hierarchy, permissions, and features

These answer different questions and should not be encoded as one `role` column:

1. **Hierarchy:** who owns or supervises whom. Siblings have equal standing. A Builder's request to change a plan or design goes to its feature lead; it does not automatically climb through Designer and Planner. Review and QA remain independent of Builder.
2. **Action permissions:** what a member may ask, delegate, answer, approve, or write. The server enforces each action using the caller's authenticated run and explicit grants. Prompt instructions are guidance, not authorization.
3. **Order of work:** which step follows which. No graph encodes it. A feature's lead decides from the brief and its instructions, and asks the person for decisions in its own thread. An earlier versioned workflow engine (stages, gates, routes and handoff records) was removed because a fixed graph kept getting in the lead's way; migration 093 drops its tables.

A bot hands a project each request with `delegate_task`, whose child is a fresh project manager. A feature's lead is a crew run of the project manager, created by [FeatureService](../../apps/server/src/features/FeatureService.ts) when the feature starts, under a run ID hashed from the feature, so starting again reuses it. Its opening message is the brief with its attachments, and its task names the crew. The lead hands work on with `delegate_task` and `crewMember`: [OrchestratorMcpService](../../apps/server/src/mcp/OrchestratorMcpService.ts) resolves the name through `CrewDelegation` to one of the feature's members, prefixes the member's instructions and uses its model, and the orchestrator stamps `feature.member` on the child. Outside a feature's lead thread, `crewMember` is refused. The [thread runtime](../../apps/server/src/crew/CrewThreadRuntime.ts) enters T3's existing orchestration engine; it does not launch provider CLIs directly. Deterministic thread and command IDs let a restart retry accepted work without creating another user turn.

Crew members are subagent threads of the lead, so they inherit its worktree and feature tag and their results return to the lead the way any subagent's does. That also means they inherit subagent limits: they drop out of the sidebar list (clients show them inside the feature's row), and their MCP tools are the lead's minus the crew tools ([crewMcpCapabilities](../../apps/server/src/crew/crewMcpCapabilities.ts)). Where a feature stands is never stored: the board's server read only names each feature's lead thread, and clients derive the column from the lead's and crew's thread shells ([crewBoard](../../packages/client-runtime/src/state/crewBoard.ts)).

## Scope and next boundaries

One environment owns a project's filesystem, provider credentials, and crew records. Remote and tunnel clients call the same authenticated RPCs as local clients. A bot spanning several environments needs its own durable home, delegated per-environment authority, revocation, and an explicit offline policy; a client tab cannot be that home.

A feature has one worktree and one branch, so its crew shares one checkout. Planner, Designer, Builder, QA Tester, and Reviewer may have separate threads and can work concurrently where their permissions and artifacts allow it; keeping concurrent writers apart is the lead's job. A member's provider runtime mode controls T3 approval behavior; it is not a grant to change another member's task, approve an artifact, push a branch, or publish to an external service. Those actions need server-side policy and attributable results.
