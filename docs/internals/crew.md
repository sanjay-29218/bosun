# Crew in T3 Code

T3 Code already gives a person durable threads and a provider runtime. Crew mode adds stable identities and durable coordination between those threads. A top-level bot, when the project has one, owns it; a project with no bot still has its manager, which runs on the project's default model, else the environment's. It receives a person's request for that project, delegates the work to the project's manager, and reports the linked result. The owning environment keeps the crew state and runs its providers; web, desktop, and mobile are clients of that environment. "Bot" is reserved for the top-level bots that own projects; everything here is crew.

## The boundaries that matter

- A **role** is reusable, environment-wide configuration: name, instructions, and provider instance and model. Planner, Designer, Builder, QA Tester, and Reviewer are starting roles, not an exhaustive enum. Users can add any role.
- A **workflow** is plain instructions and the crew roles a feature's lead can hand work to. There is no lead role: a feature's own thread leads, from the built-in lead text ([crewPrompts](../../apps/server/src/crew/crewPrompts.ts)) plus the workflow's instructions, so how features are led is edited in one place and a linked machine needs only the workflow to run one. It is not a graph: the lead reads the instructions and decides the order of work. Feature delivery (Planner, Designer, Builder, QA Tester and Reviewer) is built in and can't be deleted, because features without a workflow follow it.
- A **crew member** is an independently addressable instance of a role. It snapshots the role's revision, then has its own configuration and scope. A feature's lead and crew members belong to the feature. They and runs are snapshots, so a role or workflow edit never rewrites a running feature's crew or a started run.
- A **run** starts one T3 thread for one task. The run snapshots its member's instructions and tool grants. A continuation uses that thread; a later task gets another run. The thread remains the source for provider activity, approvals, checkpoints, and diffs. A started turn is not a completed task.
  Roles, members, and runs have separate storage in [the migrations](../../apps/server/src/persistence/Migrations.ts). Earlier migration files retain older storage shapes so existing databases can upgrade; later migrations rename and transform them. Member IDs such as `bot-manager:<project>` and the `bot-run:` thread prefix predate the Roles rename and stay, because stored runs and grants reference them. A feature lead's run ID, and so its event-sourced thread ID, is hashed from the feature and its lead's member ID. Leads started before workflows lost their lead role ran as `bot-manager:<project>` or `bot-lead:` members, so starting a feature again finds its lead run by that hash over the project's lead runs rather than assuming today's member ID; otherwise a reopened feature would start a second lead. `bot-manager:<project>` is now the built-in member a linked machine's request runs as, kept because retried requests carry it. The `crew_handoffs` tables from the retired handoff path stay for older databases; nothing reads them. The current store and validation live in [CrewStore](../../apps/server/src/crew/CrewStore.ts) and [CrewService](../../apps/server/src/crew/CrewService.ts).

## Bots as actors

A bot is not a crew member, but it acts in crew runs: a request to a project runs as the project's bot. Its authority comes from ownership, not grant rows. A bot only gets new runs on projects it owns, and a bot's run may delegate to members of that run's project ([CrewStore.canDelegate](../../apps/server/src/crew/CrewStore.ts)). Checking the run's project instead of current ownership means moving a project to another bot never strands a request or feature that is already running; only new work goes to the new owner. Ownership is `project.botId`, recorded by project events, so it replays like the rest of the project.

A headquarters lives as long as its bot, and a project's manager as long as its project, so their provider conversations keep growing. The provider compacts them. A person can start one over with `/new` or **Start new session…** (`startNewSession`, for a headquarters or a project's manager): `thread.conversation.restart` retires the provider conversation and a [briefing](../../apps/server/src/crew/headquartersFreshStart.ts) with the owner's current instructions and last few messages opens the next one. The thread keeps its messages for the person, but the model loses them, so anything a bot must still know later belongs in records it reads through tools (projects, features), not only in its chat.

## Two managers

A feature's **lead** is its own thread and ends with the feature. A **Project manager** runs the project, with no role behind it: member `project-manager:<project>`, run `project-hq:<project>`, thread `bot-run:project-hq:<project>`. It is never a workflow's lead or crew. Each crew thread gets the `crew` MCP capability; subagents of crew threads don't get it, since they aren't crew members.

The Project manager is a standing thread, like a headquarters, because what it waits on arrives long after the turn that took a request: a feature's report, a lead's question, a merged pull request. A per-request child would have ended by then. Bots and projects share one standing-run path in [CrewService](../../apps/server/src/crew/CrewService.ts) (create, pin, restore, settings sync, fresh start); the fixed thread ID is why such a thread can be archived but not deleted. Its thread's composer picks its model and mode, starting from the project's default model; its instructions are read live from its member, made on first use from built-in instructions, so a fresh install needs no starter roles for bots to hand off work; `customized_at` marks saved settings, and reset goes back to those defaults. Its `delegate_task` children are `listed`, so a request's task shows in the project like a feature. A bot keeps both ways into a project: handing a request to its manager, or, when the person asks, starting a task or feature itself, which then reports to the bot's headquarters rather than the manager (merge notices still go to the manager). A sent request is not a Lineage edge, so a bot's Lineage doesn't list the manager; the reply's link and **Open project manager** reach it.

Every thread lists the request tools (`t3_project_send`, `t3_project_requests`, `t3_project_reply`); a bot's headquarters is the usual sender. Requests are stored ([ProjectRequests](../../apps/server/src/crew/ProjectRequests.ts)), not inferred from turns, because the result that answers one arrives as a server message with no sender, often in another session. A request's post and replies have IDs derived from the request and the caller's key, so retries and restarts don't repeat them, and requests stored but never posted are posted at startup. When a manager turn that took requests ends with one unanswered, the server forwards the turn's last message only if that turn took exactly one request; with several it can't tell which text answers which, so it acknowledges each. `project_request_turns` records both, so a restart doesn't repeat them. Work started for a request carries its ID (`features.request_id`, a task thread's `projectRequestId`), so reports name it.

A manager closes issues when their pull requests merge into `staging`, so it has to hear about merges. [MergeNotices](../../apps/server/src/crew/MergeNotices.ts) reads persisted pull request snapshot updates rather than watches, because linking a pull request starts no watch and a watch can end early. For the same reason the pull request sync keeps a feature's or a manager task's pull request due on the quiet cadence until it merges or closes, even once its thread settles or is archived. A notice is keyed by project and normalized pull request, so two projects tracking one pull request each hear once and one notice names every feature and task of the project that carries it; `project_merge_notices` records it so a restart doesn't repeat it, and startup sends merges a manager missed since it existed. The server doesn't close issues itself: a pull request may cover only part of one.

## Hierarchy, permissions, and features

These answer different questions and should not be encoded as one `role` column:

1. **Hierarchy:** who owns or supervises whom. Siblings have equal standing. A Builder's request to change a plan or design goes to its feature lead; it does not automatically climb through Designer and Planner. Review and QA remain independent of Builder.
2. **Action permissions:** what a member may ask, delegate, answer, approve, or write. The server enforces each action using the caller's authenticated run and explicit grants. Prompt instructions are guidance, not authorization.
3. **Order of work:** which step follows which. No graph encodes it. A feature's lead decides from the brief and its workflow's instructions, and asks the person for decisions in its own thread. An earlier versioned workflow engine (stages, gates, routes and handoff records) was removed because a fixed graph kept getting in the lead's way; migration 093 drops its tables.

A bot hands a project's requests to its Project manager (below). Asked to work directly, it hands a project a task with `delegate_task`, whose child is a fresh task agent in that project, or a feature with `t3_feature_start`. A `delegate_task` child in another project than its parent's carries `lineage.listed`: it is still the parent's subagent for its result, stop and approvals, but lists in its own project, because a headquarters' own project is hidden. A feature started outside a feature stores the thread that started it (a subagent's top thread, so a project manager's feature reports to the headquarters). It hears headlines, never the lead's own words: a finish (`t3_feature_finish`'s summary, first line, and the feature's pull request), a failed or interrupted lead turn, and "needs you" with a link to the thread that asks. [FeatureReportReactor](../../apps/server/src/features/FeatureReportReactor.ts) sends a needs-you for a pending request on the lead or on a crew thread (a crew member's own questions excepted: its lead answers those), keyed by the request. [FeatureService](../../apps/server/src/features/FeatureService.ts) treats a lead turn that ends with nothing in the feature running, waiting or owed (the same quiet test as a child's) as the lead asking the person, keyed by the feature and the person's latest message to the lead, so repeats while it waits are dropped and the person's next message withdraws an undelivered one. A bot's headquarters hears only finishes and failures; it can't answer for the person. Progress stays in the feature's thread: earlier every lead stop woke the headquarters with the lead's full message, and most were "the Reviewer is checking it". All of these, merge notices and project-request replies go through [NoticeInbox](../../apps/server/src/features/NoticeInbox.ts), which holds them while the recipient has a run going and then sends one message, so N notices during one turn cost one more turn, not N. It drops a needs-you notice whose request was answered meanwhile, and a stage report replaces an older undelivered one about the same feature. Notices are keyed per recipient and delivered once, also across restarts. Each delivery is a command under its own digest id, because the orchestrator keeps a rejected command id rejected; a digest claimed but not marked sent counts as sent when its command receipt is accepted, and is otherwise claimed afresh, after answered questions are dropped. Start-up catch-up (the inbox's own backlog, quiet features and leads waiting on the person) runs in [one hold](../../apps/server/src/features/FeatureReportReactor.ts) that every delivery path honours, so each recipient gets one message. A top-level stop counts only when one of the feature's threads started or updated a run (not a silent idle `/compact`) after the event sequence recorded when the inbox's migration ran, so an upgrade doesn't report lead stops the old reporter skipped, while a feature still in flight then reports when it goes quiet. Only the lead (the feature's top-level thread) reports: its subagents, forks and side chats carry the feature tag too. A cross-project child drops its parent's feature tag, since that feature lives in the parent's project. A child feature reports to its parent's lead instead (below). A bot's headquarters may start features in projects its bot owns without full access. A feature's lead is a crew run of a member the feature owns, made from the built-in lead text on the project's default model by [FeatureService](../../apps/server/src/features/FeatureService.ts) when the feature starts, under a run ID hashed from the feature, so starting again reuses it. Its opening message is the brief with its attachments, and its task carries the workflow's instructions and names the crew. A run's task is part of its identity, so a started feature keeps the workflow text it started with; edits reach new features only. The lead hands work on with `delegate_task` and `crewMember`: [OrchestratorMcpService](../../apps/server/src/mcp/OrchestratorMcpService.ts) resolves the name through `CrewDelegation` to one of the feature's members, prefixes the member's instructions and uses its model, and the orchestrator stamps `feature.member` on the child. Outside a feature's lead thread, `crewMember` is refused. The [thread runtime](../../apps/server/src/crew/CrewThreadRuntime.ts) enters T3's existing orchestration engine; it does not launch provider CLIs directly. Deterministic thread and command IDs let a restart retry accepted work without creating another user turn.

A crew member gets the person's approval in its own thread, where its work is, with `crew_ask_person`: a server-owned question (`owner: "crew"`) on that thread, listed only to a feature lead's direct crew children (`crew.member`, derived from lineage rather than stored, so no grant list can withhold it). The tool returns at once, because an MCP call that waits for a person would time out, and the member ends its turn. Its delegated task stays open while the question is pending (`awaitsPerson` in the settle check), so the lead gets no result, isn't woken to answer it, and its wait ends with "waiting on the person". Answering or dismissing the question commits the member's continuation message in the same command, and only while its thread is live and its task still open, so neither a restart nor a cancel can fall between the answer and the work it resumes; the member's one-line outcome becomes the lead's result. The question's resolution re-runs settlement. [CrewApprovals](../../apps/server/src/crew/CrewApprovals.ts) closes a question nobody can act on any more (its task settled, as on a cancel, or its thread archived or deleted), at the event and again at start-up, which lets the task settle.

A feature started from one of a feature's threads, in practice by an Epic lead calling `t3_feature_start`, is that feature's child (`features.parent_feature_id`), unless it passes `parentFeatureId: null`, which starts a separate feature that stores the starter as requester instead. A child is an ordinary feature: its own worktree, branch, crew and lead thread. It isn't a subagent of the parent's lead, because a subagent shares its parent's worktree and drops out of the sidebar. So the subagent result path can't carry its report back. Instead the child reports once its work is done: its lead calls `t3_feature_finish` with a summary, or a person closes it first. [FeatureService](../../apps/server/src/features/FeatureService.ts) then queues a message on the parent's lead thread, which wakes it the way a crew result does. A model can forget that call, and a restart can cut its turn short, so the server also watches: when no thread of a child runs, queues or waits on the person, and its lead didn't report during its last turn, the parent's lead gets the child's last message as a "stopped", "failed" or "interrupted" note, once per lead turn. A child waiting on the person's answer isn't quiet; the board shows it as Needs input. Each report records its outcome and the lead run it came from (`report_outcome`, `reported_run_id`), so a later run is never covered by an earlier report, and clients can tell finished work from a lead that merely stopped: a lead that reported finished in its latest run reads as Done, while one that stopped without reporting reads as Waiting. The board groups finished work under Ready for review until its pull request merges. Closing alone isn't the trigger either, because a child is finished once its pull request is open, long before anyone closes it. `reported_at` keeps a close after a report from waking the parent again, and reopening clears it. `baseBranch` stacks a child on a sibling's branch, which must exist when the child starts.

Bots, the Library and features change outside any thread, often through an agent's MCP tool, so no thread shell carries the change to clients. The server counts each change ([CrewChanges](../../apps/server/src/crew/CrewChanges.ts)) and sends the counts as `crewUpdated` on the server-config stream, opt-in because older clients reject unknown event types. Clients re-read a list when its count moves, and the counts start over when the server restarts; the reconnect that follows delivers fresh ones.

Crew members are subagent threads of the lead, so they inherit its worktree and feature tag and their results return to the lead the way any subagent's does. That also means they inherit subagent limits: they drop out of the sidebar list (clients show them inside the feature's row), and their MCP tools are the lead's minus the crew tools ([crewMcpCapabilities](../../apps/server/src/crew/crewMcpCapabilities.ts)). Where a feature stands is never stored: the board's server read only names each feature's lead thread, and clients derive the column from the lead's and crew's thread shells ([crewBoard](../../packages/client-runtime/src/state/crewBoard.ts)).

## Scope and next boundaries

One environment owns a project's filesystem, provider credentials, and crew records. Remote and tunnel clients call the same authenticated RPCs as local clients. Bots stay environment-local: a bot's home is the environment whose database stores it, and clients list each bot once, under its home. A project owned by a bot from another environment keeps `botId` null and names that bot in `remoteBot` (home environment, bot id, and the name and home label it last sent); `botId` always means a bot in this database, so every local check (the delete guard, project manager defaults) stays correct without knowing about remote owners. Nothing matches bots by name, and nothing syncs their definitions; a same-named bot made on another environment before `remoteBot` existed is an ordinary local bot there. A bot's headquarters reaches its projects on linked environments through [BotReach](../../apps/server/src/bots/BotReach.ts): a request there runs as a task in that project on that environment, under its providers and credentials and on the model the request carries, on any linked environment (the global link list is the only control; nothing is kept per bot or manager), and only over a full-access link, for a project whose `remoteBot` names the calling bot. `delegate_task`, `t3_project_send` and `t3_feature_start` with an `environmentId` all take that path; none reaches the standing Project manager there. A request whose environment can't be reached is recorded as a waiting task and started later by the remote-task follower (see [05_remote.md](05_remote.md#pending-launches)), which also brings the task's reply back to the headquarters that started it, so that headquarters is the work's only inbox and there is no global home.

Workflows and roles move between machines only by import ([LibraryImports](../../apps/server/src/crew/LibraryImports.ts)); nothing is copied on its own. An import keeps the source's id, because workflows name roles by id, so one id has at most one source, recorded in `imported_from_json` with the source revision taken and the local revision right after; any save here makes it edited. Peer links are one-way and the source can't call its importers, so the importer does all the asking: each minute, and when the library opens, it reports what it holds over its own link (`t3_crew_link_library_sync`), learns newer revisions, and takes the exact revision the source's person sent it with `alsoUpdateOn`. Each target carries `replacesEdits`, what that person's dialog showed: a copy edited without that consent keeps its edits, including an edit saved while the sync was in flight, since the write rechecks the copy's revision. A later save that doesn't tick a machine withdraws what waited for it. The source's `library_importers` list comes only from those reports and is replaced by each one. Import, Take update and a pushed save are the same call. Before imports, the source pushed copies over its own link, so after migration 128 an importer that never linked its source shows "Link it to get updates" instead of updates.

A project cloned on several environments has one Project manager. A copy whose manager lives elsewhere names it in `remoteManager` (environment, that environment's project id, label) and refuses to open a manager of its own ([CrewService](../../apps/server/src/crew/CrewService.ts) `requireManagerHere`). Clients, not servers, decide and write the placement ([projectManagerHome](../../packages/client-runtime/src/projectManagerHome.ts)): peer links are one-way, and only a client connected to every copy sees them all, matched by repository. The rule is deterministic so two clients agree, and a client that sees a copy naming a home it can't see leaves the project alone. Moving the manager off a copy retires that copy's manager as turning it off does, but archives its thread rather than deleting anything. The manager reaches its copies through the bot path: `t3_bot_link_task` and `t3_bot_link_projects` take a manager's `home` (environment and project) besides a bot's, a linked environment accepts it only for a copy whose `remoteManager` names it, and its pending launches carry `managerProjectId`. Because the copy can't call home, the home asks each linked environment once a minute for the notices its requests' threads there received (`t3_bot_link_notices`) and posts them to the manager through its NoticeInbox, keyed so each arrives once; that is how a remote feature waiting on the person shows as blocked at home.

A feature has one worktree and one branch, so its crew shares one checkout. Planner, Designer, Builder, QA Tester, and Reviewer may have separate threads and can work concurrently where their permissions and artifacts allow it; keeping concurrent writers apart is the lead's job. Members have no runtime mode: each run has its own, full access unless the request that started it carried another. It controls T3 approval behavior; it is not a grant to change another member's task, approve an artifact, push a branch, or publish to an external service. Those actions need server-side policy and attributable results.
