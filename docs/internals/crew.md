# Crew in T3 Code

T3 Code already gives a person durable threads and a provider runtime. Crew mode adds stable identities and durable coordination between those threads. A top-level bot (Captain, or one a person adds) owns each project. It receives a person's request for that project, delegates the work to the project's manager, and reports the linked result. The owning environment keeps the crew state and runs its providers; web, desktop, and mobile are clients of that environment. "Bot" is reserved for the top-level bots that own projects; everything here is crew.

## The boundaries that matter

- A **role** is reusable, environment-wide configuration: name, instructions, provider instance and model, T3 runtime mode, and allowed crew tools. Feature manager, Planner, Designer, Builder, QA Tester, and Reviewer are starting roles, not an exhaustive enum. Users can add any role.
- A **workflow** is a lead role, the crew roles it can hand work to, and plain instructions. It is not a graph: the lead reads the instructions and decides the order of work. Feature delivery (Feature manager leading Planner, Designer, Builder, QA Tester and Reviewer) is built in and can't be deleted, because features without a workflow follow it.
- A **crew member** is an independently addressable instance of a role. It snapshots the role's revision, then has its own configuration and scope. A project's Feature manager belongs to the project and is created the first time a request or feature needs it; a feature's crew members belong to the feature. Project-level members (`bot-manager:`, `bot-lead:`, `project-manager:`) follow their role: a role edit rewrites them in the same transaction, and reuse re-checks the revision, skipping a member someone customized (`customized_at`). Feature members and runs are snapshots, so a role edit never rewrites a running feature's crew or a started run.
- A **run** starts one T3 thread for one task. The run snapshots its member's instructions and tool grants. A continuation uses that thread; a later task gets another run. The thread remains the source for provider activity, approvals, checkpoints, and diffs. A started turn is not a completed task.
  Roles, members, and runs have separate storage in [the migrations](../../apps/server/src/persistence/Migrations.ts). Earlier migration files retain older storage shapes so existing databases can upgrade; later migrations rename and transform them. Member IDs such as `bot-captain` and `bot-manager:<project>` and the `bot-run:` thread prefix predate the Roles rename and stay, because stored runs and grants reference them. `bot-manager:` also predates the Feature manager rename (`role:project-manager` became `role:feature-manager`): every feature lead's run ID, and so its event-sourced thread ID, is hashed from that member ID, so a new ID would start a second lead when a feature starts or reopens. The `crew_handoffs` tables from the retired handoff path stay for older databases; nothing reads them. The current store and validation live in [CrewStore](../../apps/server/src/crew/CrewStore.ts) and [CrewService](../../apps/server/src/crew/CrewService.ts).

## Bots as actors

A bot is not a crew member, but it acts in crew runs: a request to a project runs as the project's bot. Its authority comes from ownership, not grant rows. A bot only gets new runs on projects it owns, and a bot's run may delegate to members of that run's project ([CrewStore.canDelegate](../../apps/server/src/crew/CrewStore.ts)). Checking the run's project instead of current ownership means moving a project to another bot never strands a request or feature that is already running; only new work goes to the new owner. Ownership is `project.botId`, recorded by project events, so it replays like the rest of the project.

A headquarters lives as long as its bot, so its provider conversation keeps growing. By default the provider compacts it. A person can instead start it over (`bots.startNewSession`), or set the bot's `longConversation` to `new-session` so the crew does it past [`FRESH_START_TOKENS`](../../apps/server/src/crew/headquartersFreshStart.ts) after a quiet spell. Either way `thread.conversation.restart` retires the provider conversation and a briefing with the bot's current instructions and last few messages opens the next one. The thread keeps its messages for the person, but the model loses them, so anything a bot must still know later belongs in records it reads through tools (projects, features), not only in its chat.

## Two managers

A **Feature manager** (`role:feature-manager`) leads one feature: every feature lead's run is made from the project's `bot-manager:<project>` member, and ends with the feature. A **Project manager** (`role:project-manager`) runs the project: member `project-manager:<project>`, run `project-hq:<project>`, thread `bot-run:project-hq:<project>`. It is never a workflow's lead or crew. Each crew thread gets the `crew` MCP capability and each crew tool checks its own grant; subagents of crew threads don't get it, since they aren't crew members.

The Project manager is a standing thread, like a headquarters, because what it waits on arrives long after the turn that took a request: a feature's report, a lead's question, a merged pull request. A per-request child would have ended by then. Bots and projects share one standing-run path in [CrewService](../../apps/server/src/crew/CrewService.ts) (create, pin, restore, settings sync, fresh start); the fixed thread ID is why such a thread can be archived but not deleted. Its grants, model and mode are read live from its member, which follows its role's revision until someone saves settings for the project (`customized_at`); reset clears that. Role edits rewrite uncustomized project-level members in the same transaction, so an open thread never runs a new role with an old member. Its `delegate_task` children are `listed`, so a request's task shows in the project like a feature. A bot keeps both ways into a project: handing a request to its manager, or, when the person asks, starting a task or feature itself, which then reports to the bot's headquarters rather than the manager (merge notices still go to the manager). A sent request is not a Lineage edge, so a bot's Lineage doesn't list the manager; the reply's link and **Open project manager** reach it.

Requests are stored ([ProjectRequests](../../apps/server/src/crew/ProjectRequests.ts)), not inferred from turns, because the result that answers one arrives as a server message with no sender, often in another session. A request's post and replies have IDs derived from the request and the caller's key, so retries and restarts don't repeat them, and requests stored but never posted are posted at startup. When a manager turn that took requests ends with one unanswered, the server forwards the turn's last message only if that turn took exactly one request; with several it can't tell which text answers which, so it acknowledges each. `project_request_turns` records both, so a restart doesn't repeat them. Work started for a request carries its ID (`features.request_id`, a task thread's `projectRequestId`), so reports name it.

A manager closes issues when their pull requests merge into `staging`, so it has to hear about merges. [MergeNotices](../../apps/server/src/crew/MergeNotices.ts) reads persisted pull request snapshot updates rather than watches, because linking a pull request starts no watch and a watch can end early. For the same reason the pull request sync keeps a feature's or a manager task's pull request due on the quiet cadence until it merges or closes, even once its thread settles or is archived. A notice is keyed by project and normalized pull request, so two projects tracking one pull request each hear once and one notice names every feature and task of the project that carries it; `project_merge_notices` records it so a restart doesn't repeat it, and startup sends merges a manager missed since it existed. The server doesn't close issues itself: a pull request may cover only part of one.

## Hierarchy, permissions, and features

These answer different questions and should not be encoded as one `role` column:

1. **Hierarchy:** who owns or supervises whom. Siblings have equal standing. A Builder's request to change a plan or design goes to its feature lead; it does not automatically climb through Designer and Planner. Review and QA remain independent of Builder.
2. **Action permissions:** what a member may ask, delegate, answer, approve, or write. The server enforces each action using the caller's authenticated run and explicit grants. Prompt instructions are guidance, not authorization.
3. **Order of work:** which step follows which. No graph encodes it. A feature's lead decides from the brief and its workflow's instructions, and asks the person for decisions in its own thread. An earlier versioned workflow engine (stages, gates, routes and handoff records) was removed because a fixed graph kept getting in the lead's way; migration 093 drops its tables.

A bot hands a project's requests to its Project manager (below). Asked to work directly, it hands a project a task with `delegate_task`, whose child is a fresh task agent in that project, or a feature with `t3_feature_start`. A `delegate_task` child in another project than its parent's carries `lineage.listed`: it is still the parent's subagent for its result, stop and approvals, but lists in its own project, because a headquarters' own project is hidden. A feature started outside a feature stores the thread that started it (a subagent's top thread, so a project manager's feature reports to the headquarters), and [FeatureReportReactor](../../apps/server/src/features/FeatureReportReactor.ts) posts there whenever the lead waits on the person and each time it stops with no crew task open, skipping silent `/compact` runs. Its domain-event stream starts at the latest sequence, so at startup it also reports each open feature's latest stop and pending requests that the requester's thread doesn't hold yet. Only the lead (the feature's top-level thread) reports: its subagents, forks and side chats carry the feature tag too. A cross-project child drops its parent's feature tag, since that feature lives in the parent's project. A child feature reports to its parent's lead instead (below). A bot's headquarters may start features in projects its bot owns without full access. A feature's lead is a crew run of its workflow's lead role (the project's Feature manager for the Feature manager role), created by [FeatureService](../../apps/server/src/features/FeatureService.ts) when the feature starts, under a run ID hashed from the feature, so starting again reuses it. Its opening message is the brief with its attachments, and its task carries the workflow's instructions and names the crew. A run's task is part of its identity, so a started feature keeps the workflow text it started with; edits reach new features only. The lead hands work on with `delegate_task` and `crewMember`: [OrchestratorMcpService](../../apps/server/src/mcp/OrchestratorMcpService.ts) resolves the name through `CrewDelegation` to one of the feature's members, prefixes the member's instructions and uses its model, and the orchestrator stamps `feature.member` on the child. Outside a feature's lead thread, `crewMember` is refused. The [thread runtime](../../apps/server/src/crew/CrewThreadRuntime.ts) enters T3's existing orchestration engine; it does not launch provider CLIs directly. Deterministic thread and command IDs let a restart retry accepted work without creating another user turn.

A feature started from one of a feature's threads, in practice by an Epic lead calling `t3_feature_start`, is that feature's child (`features.parent_feature_id`). A child is an ordinary feature: its own worktree, branch, crew and lead thread. It isn't a subagent of the parent's lead, because a subagent shares its parent's worktree and drops out of the sidebar. So the subagent result path can't carry its report back. Instead the child reports once its work is done: its lead calls `t3_feature_finish` with a summary, or a person closes it first. [FeatureService](../../apps/server/src/features/FeatureService.ts) then queues a message on the parent's lead thread, which wakes it the way a crew result does. A model can forget that call, and a restart can cut its turn short, so the server also watches: when no thread of a child runs, queues or waits on the person, and its lead didn't report during its last turn, the parent's lead gets the child's last message as a "stopped", "failed" or "interrupted" note, once per lead turn. A child waiting on the person's answer isn't quiet; the board shows it as Needs you. Each report records its outcome and the lead run it came from (`report_outcome`, `reported_run_id`), so a later run is never covered by an earlier report, and clients can tell finished work from a lead that merely stopped: a child that reported finished in its latest run counts as Done, and any other feature as Ready for review, while a lead that stopped without reporting still reads as Your turn. Closing alone isn't the trigger either, because a child is finished once its pull request is open, long before anyone closes it. `reported_at` keeps a close after a report from waking the parent again, and reopening clears it. `baseBranch` stacks a child on a sibling's branch, which must exist when the child starts.

Bots, the Library and features change outside any thread, often through an agent's MCP tool, so no thread shell carries the change to clients. The server counts each change ([CrewChanges](../../apps/server/src/crew/CrewChanges.ts)) and sends the counts as `crewUpdated` on the server-config stream, opt-in because older clients reject unknown event types. Clients re-read a list when its count moves, and the counts start over when the server restarts; the reconnect that follows delivers fresh ones.

Crew members are subagent threads of the lead, so they inherit its worktree and feature tag and their results return to the lead the way any subagent's does. That also means they inherit subagent limits: they drop out of the sidebar list (clients show them inside the feature's row), and their MCP tools are the lead's minus the crew tools ([crewMcpCapabilities](../../apps/server/src/crew/crewMcpCapabilities.ts)). Where a feature stands is never stored: the board's server read only names each feature's lead thread, and clients derive the column from the lead's and crew's thread shells ([crewBoard](../../packages/client-runtime/src/state/crewBoard.ts)).

## Scope and next boundaries

One environment owns a project's filesystem, provider credentials, and crew records. Remote and tunnel clients call the same authenticated RPCs as local clients. Bots stay environment-local; the same bot on another environment is the one with the same `logicalBotKey` (Captain by id, others by name), and nothing syncs their definitions. A bot's headquarters reaches its projects on linked environments through [BotReach](../../apps/server/src/bots/BotReach.ts): a request there runs as a task of that project's Feature manager on that environment, under its providers and credentials, and only over a full-access link whose project owner has the same key. It doesn't reach that project's standing Project manager: `t3_project_send` only targets projects on its own environment, a known limit. The remote-task follower brings the task's reply back to the headquarters that started it, so that headquarters is the work's only inbox and there is no global home.

A feature has one worktree and one branch, so its crew shares one checkout. Planner, Designer, Builder, QA Tester, and Reviewer may have separate threads and can work concurrently where their permissions and artifacts allow it; keeping concurrent writers apart is the lead's job. A member's provider runtime mode controls T3 approval behavior; it is not a grant to change another member's task, approve an artifact, push a branch, or publish to an external service. Those actions need server-side policy and attributable results.
